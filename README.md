# AI 行程规划系统 v0.3

> 简历项目「AI 行程规划」的后端内核：LLM 抽取 → 实体对齐 → OPTW 排期求解 → 约束校验。

## 架构一句话

**LLM 只做「理解攻略 → 抽取景点」，排期交给确定性求解器，产出再过约束校验器。**

```
攻略文本 ──LLM抽取──▶ 景点别名 ──实体对齐(高德POI, F1 90%)──▶ 排期求解器(OPTW)
                                                                │
用户(天数/预算/偏好) ──────────────────────────────▶ 约束校验器 ◀┘
                                                                │
                                              行程JSON（高德真实通勤数据+三级缓存）
```

## 目录

```
backend/
├── models.py            # 数据模型（Spot / PlanRequest / DayPlan / UnplannedSpot / PlanResult）
├── solver.py            # 排期求解器：贪心构造（预算硬约束）+ 2-opt + 跨日搬运，通勤函数可注入
├── commute.py           # 通勤矩阵：高德 /v3/distance + JSON 缓存 + 限频节流 + 无Key自动降级
├── aligner.py           # 实体对齐：别名→高德POI（召回→打分融合→类型硬过滤→阈值分流），F1 90%
├── eval_aligner.py      # 对齐评估：20 条标注集，输出 P/R/F1 与转人工率
├── eval_set.json        # 标注集（4 城市 20 条别名→标准POI）
├── evaluation.py        # 评估实验：三方对比（朴素基线 / 真LLM / 求解器），50 组场景
├── eval_results.json    # 评估结果（seed=42 可复现）
├── constraint_check.py  # 约束校验器：预算/时间负载/通勤占比，违规即报告
├── extractor.py         # LLM 抽取：攻略文本 → 结构化景点（OpenAI 兼容接口 + 容错解析）
├── demo_data.py         # 西安 14 景点演示数据（零 Key 可跑）
├── run_demo.py          # 一键 demo：纯估算模式
├── run_demo_amap.py     # 一键 demo（高德版）：配了 Key 走真实数据，没 Key 自动降级
├── .env.example         # 配置模板（AMAP_KEY / LLM_API_KEY），复制为 .env 使用
└── main.py              # FastAPI 接口：/health /plan /extract
```

## 30 秒跑起来（不需要任何 API Key）

```bash
cd backend
pip install pydantic          # demo 只需要这一个
python run_demo.py
```

启动 API 服务（需要 fastapi + uvicorn）：

```bash

# 打开 http://localhost:8000/docs 调试 /plan 接口
```

## 已实现（v0.3）

- ✅ OPTW 启发式求解：贪心插入（收益/通勤比最优位置）+ 天内 2-opt + 跨日搬运，迭代收敛
- ✅ 时间窗硬约束：每天 [9:00, 18:00]、景点开放时间，装不下就放弃并报告
- ✅ 约束校验器：预算超支（硬）/ 日负载过重（软）/ 通勤占比 > 40%（软）/ 空天
- ✅ **通勤矩阵**：高德 /v3/distance 真实驾车时长 + JSON 文件缓存（7 天 TTL，坐标 110m 粒度）+ 限频节流（个人 Key 3QPS）+ 无 Key/失败自动降级。实测：首次求解 65 次真实调用，重复求解 0 次、4ms
- ✅ **预算硬约束**：预算在贪心构造阶段生效（不是排完再报错），放弃景点带原因（预算不足/时间窗装不下）
- ✅ **地理实体对齐（F1 90%）**：别名→高德 POI。召回 Top-5 → 打分融合（包含关系 0.55 + 字符相似 0.30 + 类型先验 0.15 + 景点后缀扩展 0.15）→ 干扰类型硬过滤（公交站/行政区/足疗店不参选）→ 置信度 <0.72 转人工。20 条标注集三轮迭代：80%（纯文本相似）→ 85%（+类型先验）→ 90%（+硬过滤+后缀扩展）
  - 已知难例 ①同名歧义：AMap 同时存在「华清池」「华清宫」新旧两个 POI ②非词汇相关别名：「紫禁城」与「故宫博物院」无字面重叠 → 修复路径：LLM 别名规范化前置
- ✅ LLM 抽取接口：OpenAI 兼容（DeepSeek/Qwen 均可）+ JSON 容错解析（剥围栏→提花括号→修尾逗号）
- ✅ FastAPI 三接口 + Pydantic 全量类型定义

## 路线图（按优先级，对应《含金量提升方案》三道硬菜）

- [x] **通勤矩阵真实化**：haversine → 高德路径规划 API，N×N 带缓存，统计调用量变化 ✅
- [x] **地理实体对齐**：LLM 抽的名字 → 高德 POI 对齐（文本相似 + 类型先验 + 硬过滤），20 条标注集 F1 90% ✅（标注集扩到 200 条 + LLM 别名规范化是下一步）
- [x] **评估实验（三方对比，50 组场景 seed=42 可复现）**：质量函数 = 0.4·(1-通勤占比) + 0.4·(1-时间冲突率) + 0.2·(1-负载不均衡)。

| 指标 | 朴素装填基线 | 真 LLM 排期 (deepseek-chat) | OPTW 求解器 |
|------|-------------|---------------------------|------------|
| 平均时间冲突数/行程 | 0.38 | 0.06 | **0** |
| 无冲突行程占比 | 62% | 94% | **100%** |
| 通勤占比 | 23.5% | 13.0% | **13.1%** |
| **预算违规** | 12/50 | **9/50 (18%)** | **0** |
| 质量分 | 0.857 | 0.918 | 0.915 |
| 单次排期耗时 | <1ms | ~800ms + API 费用 | **~1ms，零成本** |

  结论（诚实版）：给足结构化数据后 LLM 排期质量不差，但**预算控制不住**（18% 场景超支，它算不清总账）、有 API 成本与延迟。求解器保证全部硬约束且零成本。所以架构是「LLM 做理解与抽取，约束交给确定性算法」——评估数据支撑了这个设计决策。详见 `eval_results.json`。
