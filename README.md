[简体中文](README.md) | [English](README_en.md)

把一段旅行攻略文本，变成一份**约束可校验、可对话修改、地图可视**的逐日行程。

```
攻略文本 ──LLM 抽取──▶ 景点候选 ──实体对齐(高德 POI)──▶ 可求解实例
                                                          │
用户(日期/预算/时间窗/住宿) ────────────────▶ OPTW 求解器(贪心+2-opt+跨日搬运)
                                                          │
                                              约束校验器(预算/时间窗/通勤占比)
                                                          │
                                    逐日行程 JSON + WebSocket 进度 + 路书前端
```

**核心设计决策：LLM 只负责「理解」，所有硬约束交给确定性算法。**
这不是拍脑袋——50 组场景的三方对照实验显示，让 LLM 直接排期，行程质量分甚至略高（0.921 vs 0.915），
但**有 8 次预算违规、2% 的场景存在时间冲突**；本项目求解器为 **100% 合规、0 违规**。
数据见 [docs/experiments.md](docs/experiments.md)。

## 量化结果

**排期方案三方对比**（50 组程序生成场景，固定随机种子 42，详见实验报告）

| 指标 | 朴素装填基线 | **本项目求解器** | LLM 直接排期 |
|------|-------------|----------------|-------------|
| 每计划时间冲突数 | 0.38 | **0** | 0.02 |
| 无冲突率 | 62% | **100%** | 98% |
| 预算违规次数 | 12 | **0** | 8 |
| 通勤时间占比 | 23.5% | **13.1%** | 13.1% |
| 行程质量分 | 0.857 | 0.915 | 0.921 |

**实体对齐**：22 条标注集上 Precision 100% / Recall 100% / F1 100%（改进前 90%），
低置信度转人工率 13.6%（用户点选兜底）。关键机制：尾部子景点惩罚（「XX公园-远望紫禁城」≠紫禁城）、
主名权威性先验（华清池→华清宫更名重查）、LLM 仲裁兜底（低置信时在已召回候选内选优，防幻觉）。

**最优解对照**（与 OR-Tools CP-SAT 同模型、同 50 场景、同随机种子；**场景规模 8~14 景点**）：
**gap 均值 −0.03%、中位 0%、最大 0.03%、≤3% 覆盖 100%**，平均收益 79.5（最优 79.4），
单次求解均值 **501 毫秒**（CP-SAT 均值 4.08 秒）。
这个结果是"测量 → 定位 → 改进 → 复测"的产物：实验四先发现纯贪心在紧张实例上 gap 达 24%
（瓶颈在**景点选择**而非排序），据此把构造阶段改为**多起点随机重启**，gap 从 7.53% 降到 0。

**规模边界**（`backend/eval_scale.json`，另有一组 8/14/25/50 景对照实验）：
N≤8 时 CP-SAT **0.13s 即证明最优**，小规模可直接用精确解；N≥25 起 CP-SAT 撞时限只能给 FEASIBLE，
与启发式差距 ≤5%（N=50 时 CP-SAT 反超 4%：122.8 vs 117.8）。
所以「≤3% 覆盖 100%」的**作用域是 8~14 景点，不能外推到任意规模**。详见实验报告。

**模型选型**（每任务重复 5 次，详见实验报告）：免费模型在**用户等待路径**上慢 3~6 倍
（抽取 12.12s vs 1.88s、意图解析 2.56s vs 0.78s），因此交互任务保留主模型；
**后台评价生成**改用免费模型（5.74s vs 1.98s，但发生在预取阶段，用户无感）——做到「交互不降速 + 生成零成本」。

## 功能特性

**规划链路（后端）**

- **OPTW 求解器**：行程规划建模为带时间窗的定向问题，**多起点随机重启**（首轮分数降序保底、后续带抖动重跑，按 `1000·收益 − 通勤` 取最优）+ 天内 2-opt + 跨日搬运；预算在构造阶段生效，装不下的景点给出原因（预算不足 / 时间窗装不下）
- **住宿锚点**：酒店是每天的起点与终点——往返通勤计入时间窗与统计，而不是作为某个景点插入某天
- **地理实体对齐**：攻略别名（「兵马俑」「紫禁城」）→ 高德标准 POI：召回 Top-5 → 四路打分融合（包含关系/字符相似/类型先验/后缀扩展）→ 干扰类型硬过滤 → 低置信度转人工
- **通勤矩阵**：高德驾车时长 + 三级缓存（进程内 → 磁盘 → API）+ 限频节流；无 Key 自动降级为直线估算
- **约束校验器**：独立复核求解结果（预算 / 时间窗 / 通勤占比 / 空天），不信任求解器自述
- **异步任务 + 实时进度**：`/plan/async` 秒回任务 ID，后台协程执行，WebSocket 推阶段进度，轮询兜底
- **对话式修改**：LLM 解析意图（remove/add/replace/pin_add/hotel）→ 确定性代码执行 → 重排 + 复校验；支持**多轮指代**（先说「酒店是汉庭」，再说「换到西安站附近」）
- **住宿推荐与检索**：`/hotel/recommend` 打开即推荐附近酒店（无需关键词），`/hotel/search` 用关键词收窄，两者都支持 `page` 分页；POI 查询新增 `types`（住宿类别过滤）、`extensions`（取回评分等）与偏移分页；结果统一规整并做**档位归一**（经济型 / 舒适型 / 高档型 / 豪华型 / 民宿）。`PlanRequest.hotel` 会**透传并回显**——「先选酒店再规划」不再被前端门槛拦住
- **偏好权重可调**：均衡 / 少走路 / 省钱 / 多玩四种模式——权重经扫描标定，「少走路」会为省通勤主动放弃远处景点，「多玩」则放宽每天时间窗 1.5 小时。⚠️ 标定口径：**必须用「高德真实驾车时长」（线上口径）复测，不能只看 haversine 直线估算**（无 Key 兜底）——两者的量级差异会让「少走路」权重失效（详见已知局限）
- **稳健性模拟**（蒙特卡洛）：1000 次抽样估算「按时走完的概率」，并用**共同随机数**给出风险点排名——去掉哪个景点能提升多少
- **稳健排程**：用户指定「稳妥度」（如 85%），按时概率不达标就**收窄每天的排程窗口留缓冲**重排，用少量景点换确定性（实测 7 景点 3.3% → 6 景点 95.3%）
- **多城市泛化**：城市中心表（`cities.py`，坐标经高德地理编码抓取）+ LLM 抽取识别城市 + 前端城市选择器；**38 城 375 个景点**预置
- **AI 总评**：对整份行程给一次综合评价（分数 / 总评 / 亮点 / 可执行提醒），标注「门票口径」不假装已知交通花费
- **景点媒体与 AI 评价**：高德图库实景图 + 营业时间 + 地址；评价摘要由 LLM 生成并缓存，规划完成后**后台并发预取**，点开即显
- **出行天气**：按天给出「本次行程那几天」的天气（open-meteo，**免注册免 key**），降水日高亮并给一句可执行提示（备伞 / 留机动时间）。**定位是行程的注脚**：不做逐小时、不做历史气候、不做独立版块；拿不到就明说（未知城市 / 超出 16 天预报范围 / 服务不可用），**不用假数据填充**
- **五维健壮性审计**：`tools/check_backend_health.py` 用 AST 静态检查超时 / 重试 / 状态 / 日志 / 成本五条底线，**已接入 CI**，不需要密钥即可跑

**路书前端（`static/index.html`，零构建）**

- 双页结构：**规划**（表单 → 进度日志 → Day 分页行程 → 地图）与**我的**（历史规划 + 收藏景点）
- 日历区间选择（先出发后结束、区间高亮、点已选日期取消）
- Leaflet 地图按天分色路线（**7 个不同色相**：蓝 / 橙 / 青绿 / 紫 / 玫红 / 黄绿 / 靛，地图、图例、时间线与总览共用同一套配色）、图例开关、住宿锚点标记；底图可切换高德 / OSM（含 GCJ-02↔WGS84 转换）
- 景点详情卡：实景图灯箱、AI 介绍、好评 / 避雷双卡、地址一键唤起高德导航
- **酒店选择器**：打开即推荐附近酒店（携程式，无需先搜索），可搜索收窄，**分页「加载更多」**（每页 25 条）；卡片给出评分、**档位**（经济型 / 舒适型 / 高档型 / 豪华型 / 民宿）、区域、**到行程中心的真实距离**、地址、电话与多图画廊，支持「推荐 / 距离近→远 / 评分优先」排序与档位、评分筛选，一键更换（当前酒店高亮），点名称就地展开小地图（橙点=酒店、彩点=当前行程景点）判断住宿是否顺手；**没有真实房价**——高德免费接口不含房价，字段留空即不显示，**绝不编造**
- 历史规划预览 / 软删除 / 批量清理；收藏与行程联动
- **桌宠式 AI 助手「小舟」**：右下角常驻角色（sprite 序列帧，眨眼 / 呼吸 / 光标跟随 / 多状态），点击展开气泡面板；既能改行程，也能**回答行程问题**，并带**跨会话长期记忆**
- **AI 总评卡片**：分数 + 总评 + 总花费 + 亮点 / 提醒，位于稳健性模拟上方
- **出行天气卡**：稳健性卡片下方的按天天气条，降水日描边高亮；取不到时显示成一条虚线灰卡并说明原因
- **分享长图**：Canvas 手绘把整份行程导成竖版 PNG（含 AI 总评），**先弹预览浮层再「下载 / 取消」**（原先点一下就静默下载）；**零依赖、不引截图库**（地图刻意不画：高德静态图会跨域污染画布，`toBlob` 抛 SecurityError）
- 规划进度条（原进度只写进折叠日志，看着像卡住）、行程列表缩略图、右上角城市点击切换
- **modern-minimal 视觉统一**：左栏表单、右栏结果区、「我的」页与日历弹层统一到 OpenDesign `modern-minimal` 方向（发丝描边、去卡片阴影、紧字距、等宽数字、字重收敛）
- **图标规范**：全站图标改为**线性 SVG**（统一 16 视窗、`currentColor`、1.8px 描边；酒店图标采用 Lucide 的 `hotel` 造型），替换了原来的 emoji —— 仅保留桌宠 🐋 形象与代码注释里的 emoji
- **用户面文案去黑话**：hero 副标题、说明 chip、识别提示改用白话；规划进度条的阶段名换成友好文案（折叠日志里仍保留原始阶段名）
- **检索问答（RAG）**：38 城 375 景 + 223 条美食组成语料，`BM25 + 字符 bigram` 检索（**零 Key、零新依赖**）；
  每条结果带 `source` 引用并**回链核查**到库内实体（景点落坐标）；`with_answer=1` 叠加 grounded 生成层——
  **答案里提到的每个库内实体都必须出现在本次引用的片段中，否则标为「未落地」**，宁可漏报不误报；LLM 失败降级为纯检索。
  30 条 golden 集实测：BM25 **hit@1 90.0% / hit@5 100% / MRR 0.944**（语料增强前为 66.7% / 70.0% / 0.689 ——
  **短板在语料不在算法**）。**向量重排目前无显著增益**（MRR 0.950，30 条样本下 0.006 属噪声量级），
  却要引入 embedding 通道与配额依赖，故**维持 BM25**。首页有可直接试的演示框。

## 快速开始

**零 API Key 跑通**（走内置演示数据 + 直线距离估算）：

```bash
git clone https://github.com/zikkkkkking1009/ai-trip-planner.git
cd ai-trip-planner/backend
pip install pydantic
python run_demo.py
```

**启动完整服务**：

```bash
cd backend
pip install -r requirements.txt
uvicorn main:app --port 8000
# 打开 http://localhost:8000 → 点「开始规划」→ 切「地图」看路线
```

**配置 Key（可选，解锁真实通勤、LLM 抽取与 AI 评价）**：

```bash
cp backend/.env.example backend/.env
```

| 变量 | 用途 | 说明 |
|------|------|------|
| `AMAP_KEY` | 高德 Web 服务 Key | 通勤时长、POI 检索、实景图 |
| `LLM_API_KEY` / `LLM_BASE_URL` / `LLM_MODEL_ID` | 主模型 | 攻略抽取等重任务（OpenAI 兼容即可） |
| `LLM_FAST_API_KEY` / `LLM_FAST_BASE_URL` / `LLM_FAST_MODEL` | 轻任务快模型 | 评价生成；**可指向免费模型，不配则回落主模型** |
| `TILE_PROVIDER` | 底图 | 默认高德；`osm` 切 OpenStreetMap |

> 实测可用的免费轻任务模型：智谱 `glm-4-flash-250414`（0.5~0.8s 单轮；注意 `glm-4.5-flash` 与 `glm-4.7-flash` 实测 22s / 过载，不要用）。

**填完先自检，再启服务** —— `python backend/selftest.py` 会真实打一次高德与 LLM，
把三个通道标成 `ok / invalid / unreachable / missing` 并给退出码，免得「改了配置重启了才发现 Key 错了」。
服务启动时也会在后台自检一次（结果缓存 6 小时），首页「服务状态」显示的就是这个**探测过的真实可用性**，
不是「配置文件里有个值」：

| 状态 | 含义 |
|------|------|
| `ok` | 探测通过，可用 |
| `invalid` | 已配置但被上游拒绝（401 / 额度 / 模型名错 / 快通道缺 Key） |
| `unreachable` | 探测时网络不通 —— **与 invalid 分开报**，修复动作完全相反 |
| `missing` | 未配置，走设计好的降级路径 |

`/health` 的 `amap` 字段只表示「Key 是否存在」（它给 Docker healthcheck 用），
`/meta` 的 `amap_key` 才是探测过的可用性 —— 这个分工是刻意的。

## 工程实践

**测试与门禁命令**（均可无 Key 运行）：

```bash
cd backend && python -m pytest -q          # 单元测试（349 passed；依赖高德的酒店用例无 AMAP_KEY 时跳过）
cd .. && node tools/frontend_smoke.js      # 前端 jsdom 运行时冒烟（22 项）
node tools/hotel_smoke.js                  # 酒店弹层 + 长图预览 + 主题切换 jsdom 冒烟（48 项）
python tools/check_frontend.py             # 前端静态检查（10 项阻塞门禁）
python tools/check_backend_health.py       # 后端五维健壮性审计（AST，无 Key 即可跑）
python tools/check_contrast.py             # 页面级对比度门禁（解析两页 :root 令牌，零依赖）
python docs/design/contrast-audit.py --check  # 规范级对比度门禁（浅/暗两套主题各 27 组断言）
cd backend && ruff check .                 # 静态检查（pyflakes + pycodestyle 错误类，当前 0 条）
cd backend && mypy .                       # 类型检查（渐进式，当前 0 条、0 处 type: ignore）
```

> 本地与 CI 都需 **Node 22**：jsdom 30.x 的传递依赖 undici 用了 Node 22 才有的 API，
> 在 Node 20 上 `require('jsdom')` 会直接崩（2026-09-28 CI 连挂 10 次就是这个）。
> CI 里 jsdom 已钉到 `30.1.1`；要复现 CI 环境就用 `npx -y node@20 tools/frontend_smoke.js`。

> **只在本机跑**（都要真实浏览器，不进 CI：慢且脆。前置：本机 8000 在跑）：
> - `node tools/contrast_runtime.js static/index.html static/home.html --all` —— 对比度真渲染复核

## 已知局限

- **容量天花板在哪（2026-09-28 实测）**：同时在线 **3~5 人舒适、10 人明显变慢、20 人接近上限**。瓶颈是**隧道带宽而不是算力** —— 页面 310 KB 只在首屏加载时吃带宽，之后每次交互（规划 / 改行程 / 对话）只传 **2.3 KB**；单次规划 1.55 s，并发 4 人总墙钟 2.12 s（≈1.89 次/秒，求解器纯 Python 受 GIL 限制）。**真正的日天花板是高德 / LLM 平台的配额，不在代码里**
- **持久层是 JSON 文件**，无数据库与用户体系 → `/plans` 与 `/favorites` 是全局的，多用户隔离待补（ROADMAP 的 B1/B2）
- **尚未部署上线**：代码侧闸门（访问令牌 + 限流）已就绪、Dockerfile / docker-compose 也已就绪，缺一次平台侧创建（需要账号 + 实名认证）。**照做步骤见 [`docs/deploy-runbook.md`](docs/deploy-runbook.md)**（花生壳免费内网穿透 + 朋友规模定位）
- **`APP_TOKEN` 是"单令牌"而非账号体系**：拿到同一个令牌的人彼此不分、也看不到各自的数据隔离（收藏/历史仍是全局共享）。对"朋友圈娱乐"这个定位够用；要真隔离得做用户体系（B1/B2）。令牌**留空即无鉴权**，所以上公网前务必设置（`/meta.status.token_required` 会如实回报）
- **偏好权重对通勤数据源的量级敏感**：线上用高德**真实驾车时长**，而无 Key 时退回 **haversine 直线估算**（后者量级更大）。「少走路」唯一的作用是**为省通勤放弃远景点**，其触发条件是 `通勤权重 × 省下分钟数 > 1000 × 景点分` —— 数据源一换，同样的权重可能完全不触发。曾出现「少走路与均衡结果一模一样（西安 183.3 vs 183.3 分钟）」而单元测试却是绿的，因为测试只跑了 haversine 口径。**现在的回归测试用真实通勤矩阵**（无 `AMAP_KEY` 时跳过），并且要求差异 > 5 分钟而不是 > 0
- **票价区分「已知免费」与「未知」，绝不把后者显示成 ¥0**：高德免费接口**不返回票价**（景点 `biz_ext.cost` 实测为空数组，酒店 `lowest_price` 同理），攻略没写价时 LLM 只能给 0 —— 直接显示等于谎称免费。所以 `Spot` / `VisitedSpot` 各带一位 `ticket_known`，值为假时前端统一显示「**票价待查**」；已知票价会先用本地票价表（`demo_data`）回填（按**精确名字**匹配，不做模糊匹配 —— 宁可少填也不把别处票价按错）。**已知局限**：高德标准名与本地表未必一致（如「秦始皇帝陵博物院」vs「秦始皇兵马俑博物馆」），故回填覆盖率不是 100%
- **酒店没有真实房价**：高德免费接口不返回房价（`biz_ext.lowest_price` / `cost` 为空），也未接入 OTA 数据源 —— 卡片上的评分、档位、区域、距离、电话是真实的，但**价格字段留空即不显示**；同样拿不到点评数、房型、可订状态与取消政策（不估算、不编造）
- **对齐标注集只有 22 条**：F1 100% 的统计意义有限，需扩到 100~200 条（ROADMAP 的 A3）
- **稳健性模拟的噪声参数是估计值**：停留用三角分布、通勤用对数正态，参数未经真实日志标定 ⇒ **绝对概率不能当精确值**（不同参数下跨度可达 48.9pp），但风险点的相对排序对参数不敏感，主打「建议」而非百分比
- **无网络 / 无 Key 时通勤降级为直线估算**：有 `AMAP_KEY` 才走高德真实驾车时长
- **天气依赖第三方公开服务**：`open-meteo` 免注册免 key，但仍是外部依赖；预报只覆盖**未来 16 天**（更早用归档数据、有滞后），行程日期超出范围或服务不可用时**不显示天气**，只说明原因 —— 不做气候平均之类的估算

以上前两项已在 **[ROADMAP.md](ROADMAP.md)** 中列出解决方案、优先级与依赖关系。
