功能

三段链路，都不是「调个 API 就完事」

抽取要做归一化与容错解析，对齐要做类型过滤与结构性规则，排期要处理时间窗、 每日返程与预算——每一段都有自己的工程量。

OPTW 求解器

带时间窗的定向问题：多起点随机重启 + 天内 2-opt + 跨日搬运。 与 OR-Tools CP-SAT 最优解差距均值 −0.03%，单次求解 501ms（CP-SAT 均值 4.18s）。

地理实体对齐

「兵马俑」「紫禁城」这类别名 → 高德标准 POI。Top-5 召回 + 四路打分融合 + 干扰类型硬过滤 + 低置信度 LLM 仲裁（答案锁定候选集内，防幻觉）。F1 100%。

住宿锚点

酒店是每天真正的起点与终点。往返通勤计入时间窗与统计， 而不是当作某个景点插进某一天。

稳健性模拟与稳健排程

1000 次蒙特卡洛给出「按时走完的概率」与风险点排名； 指定稳妥度后收窄排程窗口留缓冲重排——用 1 个景点换 92 个百分点确定性。

对话式修改

「明天下午加个咖啡馆」「酒店换到西安站附近」。LLM 解析意图 → 确定性代码执行 → 重排并复校验，支持多轮指代。

独立约束校验

求解器说自己合规不算数——预算、时间窗、通勤占比由独立校验器复核一遍。 历史上真的抓到过优化步骤破坏不变量。

怎么工作

LLM 负责理解，算法负责合规

这条分工不是偏好，是实测结论：让 LLM 直接排期的质量分甚至略高，但会违反硬约束。

01

攻略文本

粘贴一段游记、攻略或自己想去的清单。

02

结构化抽取

LLM 抽出景点、停留时长、评分、门票，并识别城市。

03

实体对齐

别名落到高德标准 POI，拿到真实坐标，低置信度转人工点选。

04

OPTW 求解

预算、时间窗、开放时间、住宿往返一起进模型，多起点搜最优。

05

独立校验

独立复核一遍，不通过就把违规项摆出来，而不是假装没看见。

已知局限

写清楚哪里还不行

行程规划是要拿去执行的，所以宁可先说清楚边界，也不假装全知。

门票与停留时长是近似值。 坐标来自高德真实抓取，票价与停留是演示参数；高德搜索接口实测不返回票价（8 个知名收费景点覆盖率 0%），所以不编数字。
稳健性模拟的噪声参数未经真实日志标定。 绝对概率不应当作精确值，风险点的相对排序才是可用的部分。
无数据库与用户体系。 历史与收藏保存在本地文件，暂不支持多用户隔离。
无网络 Key 时通勤降级为直线估算。 配置高德 Key 后才会使用真实驾车时长。
