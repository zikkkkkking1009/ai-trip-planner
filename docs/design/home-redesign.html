01 / LAYOUT

hero 左右内边距被吃掉了

一个元素同时挂了两个类，而两个类都设了 padding。后者用简写把前者的 左右值一起覆盖成 0 —— 这是 CSS 里最典型的"看起来没问题、量起来全是问题"。

根因（2 行）

<!-- static/home.html:465 -->
<section class="hero" style="padding:0">
  <div class="wrap hero-in">          ← 一个元素，两个类

/* CSS */
.wrap    { padding: 0 var(--pad); }     ← 想提供的左右留白
.hero-in { padding: 96px 0 88px; }      ← 简写把左右也写成 0
/* .hero-in 在后，同优先级 → 胜出。左右内边距归零。*/

/* 修法：只改纵向，让 .wrap 的左右留白生效 */
.hero-in { padding-block: 96px 88px; }

实测（修复前）：hero 比全站其他区块多探出去一截

用 Playwright 打开真实页面读 getBoundingClientRect().left， 与同页其他区块的标题左边界对比。

02 / CONTRAST

首屏三行字，全部读不动

hero 是蓝色满屏。白字压在蓝底上本来就只有 4.21:1 —— 刚好低于正文所需的 4.5:1。 而实现里还额外用 color-mix() 把白字往主色里兑了一点，"让层次更细腻"。 结果是：越细腻越读不动。

浏览器实测（不是令牌推算）

取 getComputedStyle 的实际颜色、字号、字重，向上寻找最近的不透明背景色， 按 WCAG 2.2 算。大字号（≥24px，或 ≥18.66px 且加粗）下限 3.0，其余 4.5。

元素字号/字重实测下限判定
hero 主标题62px / 8004.18:13.0通过
hero 副标题16px / 4003.64:14.5不达标
hero 次按钮文字16px / 6004.18:14.5不达标
hero 补充说明12px / 4003.14:14.5不达标
导航链接14px / 4004.92:14.5通过
指标卡数值28px / 8004.32:13.0通过

为什么 color-mix 是元凶

color-mix(in oklab, var(--accent-ink) 88%, var(--accent)) 的意思是 "88% 的白 + 12% 的主色"。它让文字看起来略微偏蓝、更"融入"背景 —— 但对比度从 4.21 掉到 3.64。换了 0.57 的对比度，换来的是肉眼几乎看不出的色偏。

实测：底色亮度决定一切

表格是"该底色下，白字能拿到多少对比度"。判定列要求三行字全部 ≥4.5。

hero 底色纯白字副标题 88%说明 76%判定
oklch(58% 0.18 255) 现状4.213.653.15❌
oklch(55% 0.18 255)4.784.113.49❌
oklch(52% 0.19 255) = --accent-deep5.414.603.86note 仍差
oklch(46% 0.18 255)6.955.784.74✅ 全部通过

两条路：① 把底色压到 46% 才够——会明显变深； ② 去掉 color-mix，副标题与说明一律用纯 --accent-ink， 底色只需 52%，白字 5.41:1，三行全部通过。
层次改由字号（62 / 16 / 12）承担——原来那 12% 与 24% 的色偏， 肉眼分不出来，代价却是把最需要读的那行压到了 3.14:1。

这也暴露了上一轮门禁的盲区
tools/check_contrast.py 只看 :root 里的令牌取值， 而 color-mix() 生成的是运行时动态颜色，不在令牌表里 —— 所以门禁报了「通过」，浏览器却量出 3.64:1。
已在本轮补上：门禁现在会扫出页面里的 color-mix 用法并列为待人工复核项。

首页的主按钮是黑底，规划器的主按钮是蓝底。 两处各写各的，谁也没错，合起来就是"点进去像换了个网站"。

两个独立缺陷

  • 语义反用：background:var(--fg) 把"文字色"当背景用。 改主题时这一处最容易漏。
  • 字面值未令牌化：oklch(16% 0.012 250) 在 .hero-cta 和 .cta 里各写一遍，不在 :root。
  • 对比度不够：规划器蓝底白字只有 4.34:1，低于 4.5 —— 已在 上一轮列入历史债。

为什么不能统一成"全是蓝按钮"

hero 本身就是满屏主色。在蓝底上放蓝按钮＝按钮消失。 彩色区块内的主按钮必须反转：

  • hero 内：白底 + 深蓝字（实测 6.04:1）
    按钮块自身压 hero 底 6.06:1
  • hero 外（导航 / 页尾 CTA）：主色实心 + 浅字
    与规划器同一套，点进去不跳色

07 / GUARDRAIL

配套：对比度门禁已接入 CI

上面这些数字，如果没有机器守着，下次改配色还会再犯一遍。新增的 tools/check_contrast.py 已挂进 tools/check_frontend.py， 成为 CI 里的第 9 项检查。

它怎么工作

  • 从 static/index.html 与 static/home.html 解析真实令牌（oklch() 与 hex 都支持）
  • 按「令牌 × 参照底」断言 —— 因为同名令牌在两页角色完全不同 （--muted 在首页是正文主力，在规划页是零引用死令牌）
  • 阈值按实际用法自动收紧：某令牌一旦有文字用法 （含 SVG <text> 的 fill），就必须满足 4.5
  • 已知历史债走白名单，但白名单登记了令牌原始值 —— 值被改动即失效，避免"记账"退化成"永久免疫"
  • 余量 < 0.15 的达标项会被标为贴线，提醒改动时优先复测

跑法

# 实测报告（含每档角色、参照底、用法分布）
python tools/check_contrast.py

# 门禁：不达标退出码 1
python tools/check_contrast.py --check

# 自测：验证门禁真的拦得住
python tools/check_contrast.py --selftest

# 债务清零后开严格模式
python tools/check_contrast.py --check --no-debt

# 运行时实测：遍历每个文字元素（需本机 Chrome/Edge）
node tools/contrast_runtime.js static/home.html static/index.html
node tools/contrast_runtime.js static/home.html --dark

结论要调整：这不是「几处令牌不达标」
41 + 18 项说明整套灰阶与语义色整体偏浅，而不是零散的手误。 成因一致：设计时按「浅色底上好看」挑值，没有按「最坏背景下的对比度」反解。 所以批 2 要按 令牌系统性重解（本文件 §4 给的就是反解出来的值）， 而不是逐个元素打补丁。
✓ 门禁做了自测，因为"没被测过的门禁等于没有门禁"
自测会在内存里故意改坏页面副本，确认： ① 把 --muted-3 从 68% 调淡到 82% 会被拦下； ② 注入一个未登记角色的颜色令牌会被提示； ③ 把某个令牌改到达标会提示"可从债务表删除"。
第 ① 条第一次跑就抓出了设计缺陷：白名单原本只按令牌名豁免， 导致"改得更糟"也被静默放过 —— 这就是自测存在的意义。
⚠ 门禁仍有一个盲区（本轮已部分补上）
它只看 :root 里的令牌取值，看不到 color-mix() 这类 运行时动态颜色 —— 这正是首页 hero 副标题 3.64:1 却没被拦下的原因。
本轮做了两件事：① 静态门禁补上「扫出 color-mix 用法并列为待复核」； ② 把那套测量脚本固化成 tools/contrast_runtime.js —— 遍历页面上每一个文字元素，读 computedStyle 并向上找最近的不透明背景。
它刻意不进 CI：需要真实浏览器，会给流水线增负担。 定位是「改完配色本地跑一次」的验收工具，与静态门禁一快一慢、一粗一细互补。
