6 条判断，每条都有实测数字

如果只看一屏，看这里。下面每个数字都能在本文档后续章节里找到对应表格与复现脚本。

01
问题不是「不好看」，是没有刻度
实测 static/index.html：字号 11 档（10/11/12/13/14/15/16/18/19/20/28）、 padding 12 档（2~14 奇数散值）、gap 10 档、圆角 9 档（7/8/9/10/12/14/16/18/999）。 其中 13/14/15px 三档贴在一起、8/9/10px 三个圆角肉眼不可分辨 —— 视觉随机性来自没有刻度，不是配色。 这也是「改一处崩三处」的工程根因。
02
色彩方向是对的，不要换
oklch 中性色阶 + 语义色保留十六进制（红=危险/绿=成功/橙=注意）—— 这是整套 UI 最扎实的部分， 连注释都写清了「为了统一色空间而改动语义色不划算」。换配色是负收益。本方案只补两件事： 把每档色绑定到唯一职责，以及补暗色。
03
6 处对比度不达标，其中 3 处用户每天都在摸
--muted-3 = 2.88:1（低于 4.5:1，却被引用 50 次）； 输入框占位符 2.64:1；实心主按钮白字 4.21:1（差 0.29）； --warn 作正文 3.58:1；--note-ink 4.41:1； --ok 作图形 2.62:1（它的 ink 档达标，所以只看文字会漏掉这一处）。 注意：上一个 commit「线性图标太淡看不见」修的是描边粗细（1.6→1.8px）， 但根因是颜色只有 2.88:1 —— 描边加粗并没有解决达标问题。
04
项目没有暗色主题，这是唯一的真空白
全文件 0 处 data-theme / prefers-color-scheme。 本方案给出一整套暗色令牌，并且逐档实测达标（主文字 14.52:1、元信息 4.72:1、图形边界 3.16:1）。 暗色不是锦上添花 —— 它是「这套令牌能不能脱离浅色独立成立」的证明。
05
建议做「收敛 + 补暗色 + 补实测」，不建议重做
ROADMAP 已认定产品体验达标且不该再加 UI，你自己的判断也是「UI 已超标」。 重做一遍界面只会把已有成果归零，对简历是负收益。 真正稀缺、能在面试里扛住追问的是：怎么定 token、怎么用实测证明达标、怎么让收敛不引入回归。 本方案就只给这三样。
06
交付物落地成本：改的是令牌与取值，不是结构
收起散值属于低风险批量替换（字号/间距/圆角各一张映射表，见 §2）， 不改 HTML 结构、不加依赖、不动 API、不影响 tools/check_frontend.py 的 9 项门禁。 暗色主题是唯一的净新增，用 [data-theme] 挂载，浅色零改动。

1.3 一句话根因

颜色系统是好的，尺度系统是不存在的。于是所有「层级」只能靠字重（700 用了 34 次）和颜色加深来硬撑， 而撑层级用的那档颜色恰好只有 2.88:1 —— 视觉层级与可读性被同一根绳子拽着，一拉就断。

2.5 阴影与动效 · 不动

三级阴影（--sh-1/2/3）与缓动体系（--e / --e-out / 三档时长） 在实测中没有问题：--e-out = cubic-bezier(.16,1,.3,1) 是指数缓出， 正是动效该有的做法；阴影只在表达「浮起」时使用，层级与高度语义一致。 这两项是这套 UI 里做得对的部分，收敛时不要动它们 —— 这是本方案唯一「不改」的章节。

这一处是门禁挖出来的，不是肉眼发现的：--ok 作为图形（不是文字）压在白色上只有 2.62:1，低于图形所需的 3:1 —— 但它的 ink 档（6.03:1）一直达标， 所以只看文字会漏掉。这是「一个颜色同时承担文字与图形两种角色」时可读性最容易被漏掉的地方。
还有一条工程教训值得记：不要把值解到「刚好等于阈值」。初版把每档都反解到精确的 3.00:1 / 4.50:1， 但 oklch 取值四舍五入成 hex、以及 --accent-ink 并非纯白（#f7fcff）这两件事， 会把结果重新推回线下 —— 门禁一次跑出 4 项「差 0.01~0.03」的失败。 最终统一留 0.10~0.12 的比例余量（如 --icon 定 #8c939c 实测 3.10:1， 而不是贴着 3.00:1 的 #8f969f）。设计令牌要能扛住取整与换算误差。

3.3 三天配色 · 不引入新色

原实现用硬编码 7 色（DAY_COLORS），一屏最多同时出现 7 种颜色。 改法：同色相（255）不同明度，观感是「同一族的三档深浅」，不是七个独立色。 且按主题分两套 —— 因为同一档在浅底与暗底上不可能同时达标。 块内标签色统一用 --on-accent：浅色主题是亮字，暗色主题是深字。

组件状态一览（可直接 hover / 点击／Tab 试）

§6 · 无障碍核对表

把 a11y 从「心里知道」变成「门禁可查」

这一节是整份方案里最能在面试中扛追问的部分：它不是「我注意了无障碍」， 而是「我实测了 21 组，发现 5 处不达标，用反解把每一档调到刚好达标，并且留下了可复跑的脚本」。

WCAG 2.2 条目要求本项目现状本方案动作状态
1.4.3 对比度（最小） 正文 ≥4.5:1 元信息 2.88:1、占位符 2.64:1、主按钮 4.21:1 不达标 反解出 --text-3 56% / --placeholder 55% / --accent-solid 56.4% 已修复并实测
1.4.11 非文本对比度 图形与控件边界 ≥3:1 线性图标 2.88:1 不达标；输入框边界用纯装饰色（1.27:1） 新增 --icon(3.10:1) 与 --border-strong(3.10:1)，把「装饰线」与「可交互边界」拆成两个令牌 已修复并实测
2.4.7 焦点可见 键盘焦点必须可见 无统一焦点样式，依赖浏览器默认 统一 2px --focus + 2px outline-offset；--focus 浅色 4.22:1 / 暗色 7.19:1 新增
2.5.8 目标尺寸（最小） 可点击目标 ≥24×24px 小 chip / 小图标按钮高度 32px，接近下限 @media (pointer:coarse) 下小控件统一抬到 40px；图标按钮 32px 起并保证内边距 新增
2.3.3 动画可关闭 尊重「减少动态效果」 无 prefers-reduced-motion 处理 全局兜底 *{transition:none;animation:none}，骨架屏动画一并停止 新增
1.3.1 信息与关系 语义结构正确 状态标签、按钮多为 div + 事件 交互元素统一用 <button> + aria-pressed；tab 用 aria-selected；输入框配 <label for> 需随重构落地
1.4.1 不只靠颜色 信息不能只用颜色表达 错误态仅红框；Day 靠颜色区分 错误态「红框 + 文字」双通道；总览轨道每块带景点名文字；图标全带文字标签 已覆盖
1.4.4 文本缩放 200% 放大到 200% 不丢内容 未验证；布局以 px 固定为主 收敛到 7 档字号后，关键容器改用 8pt 间距 + 弹性布局，避免 px 硬宽 需实测

6.1 可复跑的实测脚本

规范里的数字不该只活在这份 HTML 里。本轮所有换算与反解都收敛成一个零依赖 Python 脚本， 放在 docs/design/contrast-audit.py：读令牌、换算 sRGB、算 WCAG 对比度、按角色反解达标亮度。 它可以直接接进现有 tools/check_frontend.py 的门禁体系，变成第 10 项检查 —— 从此「有人改了颜色导致不达标」会在 CI 就被拦下，而不是等用户说「字太淡」。

建议的门禁用法：把 :root 与 [data-theme] 里的令牌表解析成字典， 对每组「前景色 × 它的参照底」断言对比度下限；新增令牌若没在断言表里登记就失败。 这样令牌表与断言表会强制同步，不会再出现 --muted 那种「定义了 0 次引用」的死令牌。
§7 · 待拍板的 5 个决策点

每个都给了推荐，你只需要否掉不同意的

这 5 项与 docs/plan-page-redesign.md §十一 一一对应，但这里把选项画出来了， 而不是让你读文字想象。推荐项已用主色标出。

1桌宠「小舟」的出现时机？
推荐规划完成后才出现
首次进入的焦点完整让给引导卡；出结果时它招手说「已经生成，看看要不要改」，此时它才真的有用。
选项 B常驻但首次不打招呼
保留品牌存在感，但空状态里它仍是一个会动的东西，仍然抢焦点。
理由：空状态阶段它没有可说的话。一个有嘴但没内容的吉祥物，只会稀释引导卡。
2单天视图的右栏小地图，所有宽度都给还是只在桌面？
推荐仅 ≥820px 显示
窄屏时隐藏小地图，时间线占满宽。见稿 B —— 窄屏下地图挤压时间线比没有地图更糟。
选项 B所有宽度都给
信息完整，但手机上时间线被压到 60% 宽，景点名要折行。
理由：信息优先级明确 —— 时间线是主，地图是辅。空间不足时砍辅不砍主，这是唯一正确的取舍方向。
3字重体系是否改成「700 主标题 / 600 标题 / 500 强调 / 400 正文」？
推荐同意四档，700 仅主标题
现有 700 的 34 处中约 26 处降为 600。层级改由「字号 + 颜色」承担，这是更可持续的做法。
选项 B保留 700 为主标题档
改动面小，但 700 通胀继续，标题与正文的层级依然靠「更粗」硬撑。
理由：字重是最弱的层级手段 —— 它在小字号上几乎不可感知，却会让整页「发黑」。字号和颜色才是主手段。
4落地的批次划分？
推荐三批，每批可独立验收
批 1 令牌收敛（纯替换，零结构改动）→ 批 2 尺度收敛 + 5 处对比度修复 → 批 3 暗色主题 + 界面稿 A/B/C/D。见 §8。
选项 B一次全做
总时长更短，但一旦出问题回滚半径覆盖全部改动，且无法定位是哪一层引入的。
理由：令牌替换是可机械验证的（替换后跑一次对比度脚本 + 截图比对），它必须单独成批 —— 把它和结构改动混在一起，出问题就分不清是取值错了还是结构错了。
5是否同步更新 README / CHANGELOG？
推荐是，并加一节「设计令牌」
README 里补一节令牌表与对比度实测结论，让「为什么是 56% 而不是 68%」有据可查。文档一致性目前是掉分项。
选项 B只改 CHANGELOG
成本更低，但下一个人（或三个月后的你）会重新问一遍「这个值是怎么定的」。
理由：项目已有「文档更新速度跟不上功能增长」的教训。这次改动本身就是关于取值的决策，不记录取值依据，下次一定会重做一遍推导。
§8 · 落地顺序

三批，每批独立可验收

排序原则：先把「取值」和「结构」解耦。令牌收敛不碰 DOM，可以先用最少风险把地基铺平； 对比度修复紧随其后，因为它有客观验收标准（数字达标）；结构改造放最后，因为它最需要反复看图。

批次内容改什么 / 不改什么验收方式风险
批 1
令牌层		 建 7/4/8/4 尺度令牌；把现有散值批量 snap 到最近档；删死令牌 --muted，把 --muted-2/3 重命名并绑定职责 只动 CSS 取值，不动任何 DOM 结构与 JS 替换前后各跑一次 contrast-audit.py；对比截图存档 低 纯替换，可整批回滚
批 2
可读性		 5 处对比度修复：--text-3 / --placeholder / --accent-solid / --warn-ink / --note-ink；补 --icon 与 --border-strong；顺带修方向 E 的颜色收敛（Day 色、chip 色） 动色值 + 少量选择器；仍不动结构 对比度脚本全绿（这是客观标准，不靠肉眼）；顺带把脚本接进门禁 低
批 3
结构与主题		 挂 [data-theme] 暗色主题；落地界面稿 A（空状态 + 三段表单）、稿 B（时间线）、稿 C（总览）、稿 D（结果区顺序）；修 plan-page-redesign.md §四 的 5 个 bug 动 DOM 结构与 JS；不动后端契约、不加依赖、不拆文件 tools/check_frontend.py 9 项门禁 + 前端冒烟 + 明暗两套截图 中 需注意 shareImage() 依赖结果区内部结构

8.2 一句话总结

这套方案的价值不在「4 张新界面」，而在三样可以复用的东西： 一套有刻度且每档都有职责的令牌表、一份 21 组的对比度实测报告、一段能自动拦回归的门禁断言。 界面会继续改，这三样会一直用下去。
