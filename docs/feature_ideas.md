# 候选功能池（2026-09-19 整理）

> **筛选标准**：这个项目的第一目标不是产品成功，是「**能写进简历、能扛住面试追问**」。
> 所以下面每条都标了「**对求职的价值**」，而不是「有多少用户会用」。
> 已经在 ROADMAP 里立过项的（B1/B2 数据库、A3 标注集、C1 前端拆分等）不再重复。

---

## A 档｜成本低、面试可讲（建议最近做）

### A1. 决策解释面板
- **作用**：把求解器的"黑盒"变透明——展示每天为什么排这些景点、哪些被淘汰及原因（`unplanned` 的 reason 已有）、通勤占比与负载占比。
- **对求职的价值**：**面试可直接指着界面讲**「系统不只给结果，还给依据」。这是「可解释性」，比多一个功能页值钱得多。
- **成本**：低。数据**已经在** `check_report` 和 `unplanned` 里，缺的只是前端展示。
- **依赖**：无。

### A2. 偏好权重可调（省钱 / 少走路 / 兴趣优先）
- **作用**：把 `Spot.score` 与通勤权重暴露成用户可调的滑块（如「门票敏感度」「步行容忍度」），实时重排。
- **对求职的价值**：把「多目标优化」从论文概念变成**用户可感知的产品功能**。面试问「你的目标函数怎么定的」时，可以答"我把它产品化了，用户能调"。
- **成本**：低~中（后端只改权重入口，`SCORE_OBJ_W` 与 `score` 已是参数化结构）。
- **依赖**：无（与 A1 天然搭配，同一个面板里做）。

### A3. 行程导出（日历 .ics / Markdown / 复制文本）
- **作用**：一键把行程导进手机日历、发微信、存 Markdown。
- **对求职的价值**：端到端闭环的最后一环——「生成的行程真的能用」。成本极低，但让演示有"完成感"。
- **成本**：低（纯前端 + 一个文本生成接口）。
- **依赖**：无。

### A4. 移动端适配（响应式）
- **作用**：手机上正常查看地图、详情卡、行程卡片。
- **对求职的价值**：**面试官大概率用手机点开你的链接**。桌面端完美但手机端错位 = 第一印象打折。
- **成本**：低~中（单文件 HTML，加媒体查询 + 触控尺寸调整）。
- **依赖**：部署前必做。

### A5. 错误兜底与中文提示
- **作用**：LLM 超时、高德限流、无 key 时给明确中文提示 + 降级路径，而不是 500 白屏。
- **对求职的价值**：健壮性的可见体现。目前已知 `/extract` 只 catch 三类异常，`retry_call` 抛出的原始异常（`APITimeoutError`）会穿透成 500。
- **成本**：低。
- **依赖**：部署前必做（与配额保护同批）。

## B 档｜技术含量高（10~11 月做）

### B1. 自适应求解器（小规模走 CP-SAT 精确解）
- **作用**：同一接口按问题规模自动选路——景点数少时用 CP-SAT 求**精确最优**，规模大时用启发式（多起点 + 2-opt）。
- **对求职的价值**：把已有的 `solver_cpsat.py` 从「实验脚本」升级为「生产能力」。面试问「为什么不用精确解」时可以答「我用，只是按规模自动切换」——**并且有 gap 实验数据支撑**。
- **成本**：中（求解器接口归一化 + 规模阈值调参）。
- **依赖**：`requirements-eval.txt`（ortools）需进运行时依赖。

### B2. 方案对比视图（省钱版 / 高效版 / 深度版）
- **作用**：同一批景点生成 3 个不同权重下的方案并列对比，用户挑一个。
- **对求职的价值**：多目标优化的产品化展示，比单方案更能体现算法能力。
- **成本**：中。
- **依赖**：A2（权重可调）先做。

### B3. 可观测性 + 压测报告
- **作用**：`/metrics` 暴露 QPS、P50/P95 延迟、缓存命中率、LLM 调用耗时分布；用 k6/Locust 压测并发 50。
- **对求职的价值**：工程硬数据——「并发 50 时 P95 延迟 X ms」比「我写了缓存」有说服力得多。
- **成本**：中低。
- **依赖**：无（可在本地压测，不需要上线）。

### B4. 通勤矩阵预热
- **作用**：热门城市（西安/成都/北京/杭州）的两两通勤提前预抓取入库，首次规划也秒出。
- **对求职的价值**：性能优化故事，且直接改善演示体验（现在首次规划要等 10~30 秒）。
- **成本**：低~中（复用已有三级缓存，只是加批量预取）。
- **依赖**：无。

## C 档｜升格项目定位（秋招前，成本高）

### C1. RAG 攻略库
- **作用**：把攻略/游记文本向量化入向量库，支持「按兴趣检索景点」「基于攻略片段生成行程说明」。
- **对求职的价值**：**最强的差异化标签**——项目从「LLM + 算法工具」升格为「AI 应用」。2027 届实习岗超九成与 AI 相关，这个标签直接对口。
- **成本**：中高（向量库选型、切分策略、检索评估）。
- **依赖**：建议在数据库（B1/B2 主项目）之后做。

### C2. 行程分享（只读链接）+ 分享长图
- **作用**：生成只读分享链接或长图，发给旅伴。
- **对求职的价值**：产品完整度信号，非核心。
- **成本**：中（长图需前端渲染截图方案）。
- **依赖**：用户体系（B2 主项目）之后。

## 建议的动手顺序

```
A5 错误兜底 + 配额保护   ← 部署硬前提（1 次会话）
A1 决策解释面板 + A2 权重可调   ← 一批做，面试最好讲（1~2 次会话）
A4 移动端适配 + A3 导出        ← 演示体验（1 次会话）
B3 压测报告 + B4 通勤预热      ← 工程硬数据（1 次会话）
B1 自适应求解器                ← 技术深度（1~2 次会话）

```

**一句话原则**：优先做「把已有算法能力翻译成用户可见功能」的事（A1/A2/B1），
而不是「加新能力」的事——你的算法内核已经很扎实，缺的是让它**被看见**。

# 第二部分：泛化与深度功能（2026-09-19 增补）

> **背景**：周周指出「功能太基础、只有西安一个城市、泛化没处理」。
> 查证后确认**他判断正确，且我此前把 C4 多城市放在 C 级是误判**——这不是锦上添花，
> 是「产品能不能用」的分水岭。以下第一部分是诊断证据，第二部分是新功能建议。

## 一、泛化现状诊断（查证结论：当前是「西安专用 demo」，不是通用产品）

### 前端硬编码（`static/index.html`，4 处）

| 位置 | 代码 | 后果 |
|------|------|------|
| 415 行 | `const req = { city:'西安', days: dayCount(), ...` | **规划请求永远带西安** |
| 515 行 | `city: '西安'`（编辑操作） | 换酒店/搜索都限定西安 |
| 630 行 | 兜底文案「是**西安**的热门去处」 | 文案错 |
| 906 行 | `city: '西安'`（POI 搜索） | 搜不到其他城市 |

### 后端

- `demo_data.py`：只有西安 14 个景点；`main.py:161` demo 接口写死 `{"city": "西安"}`。
- `models.py:44`：`PlanRequest.city` 默认 `"西安"`。
- `tasks.py`：4 处 `params.get("city", "西安")`。
- **`extractor.py:84`（最隐蔽的杀手）**：抽取阶段的**兜底坐标是西安的**（`lat=34.26, lon=108.94`）。

### 静默错误链（这才是真问题）

```
用户粘一段成都攻略
  → 前端把 city 写死为「西安」
  → 对齐器按 citylimit=西安 搜「宽窄巷子」→ 空结果
  → 景点坐标仍是兜底值（西安坐标）
  → 求解器照常排期、照常通过约束校验、照常返回结果
  → 用户看到一份「坐标全在西安、景点名是成都」的行程，且系统不报任何错
```

**这是"静默错误"，比报错更危险**——报错用户会重试，静默错误用户会认为产品就是坏的。

### 修正结论

| 项 | 我此前的判断 | 修正后 |
|---|---|---|
| C4 多城市 / 泛化 | C 级「锦上添花」 | **A 级（最高优先）**：决定产品是否可用 |

## 二、新功能建议（按「技术深度 × 面试可讲性」排序）

### ✅ N1. 多城市泛化（架构级重构）——**已完成 2026-09-19**
**作用**：让任意城市可用，而不是只有西安。
**完成情况**：城市中心表 `cities.py` + LLM 抽取识别城市 + 前端城市选择器与攻略入口 + 5 城 54 个景点（高德真实坐标）+ 33 个新测试；端到端验证「成都攻略 → 识别成都 → 8 个景点全落在成都坐标 → 2 天行程全部排入」。

**完成后的新发现（转下一轮）**：
- **对齐到子景点**：抽「成都大熊猫繁育研究基地」会对齐到「…-熊猫塔」、「杜甫草堂」→「…-杜陵村」。A7 的尾部惩罚只覆盖「长前缀 + 别名在尾部」，这类「别名 + 短后缀子点」没管 → 记为 **A8**。
- **门票全为 0**：抽取路径 LLM 拿不到票价（攻略里没写），演示时「总门票 0 元」显得假 → 可从高德 `avg_cost`（人均消费）或 demo 数据补齐，但要区分「人均消费」与「门票」的语义差别。

拆成 4 个子任务：

1. **城市参数全链路打通**：前端加城市选择器；**LLM 抽取时顺带识别攻略所属城市**（自动填），彻底移除 4 处硬编码。
2. **兜底坐标城市化**：抽取的兜底坐标从「固定西安」改为「该城市中心」——用一张城市中心表（离线可用）或高德地理编码 API（`extractor.py:84` 的 TODO）。
3. **demo 数据扩到 5 城**（西安 / 成都 / 北京 / 杭州 / 重庆），保持「零 Key 可演示」。数据可脚本化预抓取（复用 `fetch_spot_details.py`）。
4. **缓存按城市隔离**：POI 缓存 key 已含 city ✅；通勤缓存以坐标为 key ✅ 天然隔离——但要复核跨城市坐标碰撞。

**验收**：粘一段任意城市攻略 → 端到端跑通 → 行程坐标全部落在该城市。
**面试价值**：ROADMAP 里预判的追问「扩展新城市要改什么」，你现在的答案很弱（"只换 demo 数据"）。做完后能讲：**哪些当初被硬编码、如何做到参数化、泛化的边界在哪**——这是工程成熟度的直接体现。
**成本**：中（前端改造 + 抽取加字段 + demo 数据脚本）。

### N2. 地理聚类分天（算法升级 + 实验闭环）★性价比最高
**作用**：现在的贪心按「通勤/score 比」逐个插入，**天与天之间没有地理聚类**——可能出现「城东城西各排一半」的绕路方案。

**改法**：构造阶段前先做地理聚类（k-means 或按经度扫描线切分），让每一天对应一个地理簇，再在天内跑 2-opt。
**预期收益**：通勤占比从 **13.1%** 继续下压（有机会进 10% 以内）。
**验收**：复用 `eval_gap.py` 的 50 场景框架做改前/改后对照，结果写进 `docs/experiments.md` 实验五。
**面试价值**：这是你项目**方法论的完美闭环**——「发现指标瓶颈 → 提出假设 → 改造 → 对照实验验证」。比"我加了个功能"有说服力得多。
**成本**：中（聚类 50 行 + 实验脚本复用）。

### N3. 行程稳健性模拟（不确定性建模）★技术深度最高
**作用**：现在所有时间都是确定值（停留 90 分钟、通勤 43 分钟），但真实世界有波动（堵车、排队、找不到入口）。

**改法**：蒙特卡洛仿真——给停留时长与通勤时长加噪声分布，跑 500 次，输出：
- 「这份行程按时完成的概率 **82%**」
- 「主要风险点：第 2 天 16:40 华清宫→市区段（晚高峰）」
- 「若给每个景点 +15 分钟缓冲，概率升至 95%」

**面试价值**：**最高**。把「确定性优化」升级为「**鲁棒优化**」，涉及概率建模、仿真、置信区间。这是能让你和其他候选人拉开差距的话题，因为它证明你不只会写代码，还会**给结果标注不确定性**。
**成本**：中高（仿真框架 + 风险归因 + 前端展示）。

### N4. 反事实分析引擎（「如果」查询）
**作用**：回答「如果……会怎样」——
- 「预算提到 800，能多排哪几个？」
- 「华清宫闭馆了，行程怎么变？」
- 「下雨只玩室内景点？」

**改法**：参数化重跑 + 结果差分展示（对比视图）；进阶做**增量求解**（只重排受影响的天），增量 vs 全量的耗时对比本身就是一份可讲的实验。
**面试价值**：决策支持系统设计 + 增量算法。
**成本**：中。

### N5. 帕累托多方案（多目标优化）
**作用**：同批景点生成非支配解集合（时间最优 / 费用最优 / 体验最优），前端画帕累托前沿。
**面试价值**：多目标优化的标准话题，且可复用已有的 `solver_cpsat.py`（CP-SAT 天然支持多目标约束）。
**成本**：中。

### N6. 主动澄清式抽取（人机协作升级）
**作用**：现在低置信度 → 标记「转人工」→ 用户自己点选。改成 **LLM 主动追问**：
> 「你说的『陕历博』是指陕西历史博物馆吗？」（给 2~3 个候选按钮）

用户选择后**回填并写入缓存**，下次同样输入直接命中。
**面试价值**：交互设计 + 置信度分流，比"转人工"高一个层次；且能讲"澄清成本 vs 静默错误成本"的权衡。
**成本**：中。

### N7. 多篇攻略聚合（信息融合）
**作用**：用户贴多篇攻略 → 同一景点的停留时长/评分取加权中位数 → **冲突检测**（A 篇说 2 小时、B 篇说 4 小时，标记出来）。
**面试价值**：数据融合 + 冲突消解，有具体的工程问题可讲。
**成本**：中。

### N8. URL 抓取攻略（数据入口扩展）
**作用**：贴马蜂窝/小红书链接 → 抓正文 → 抽取。
**风险**：反爬 + 合规。**不建议现在做**（收益与风险不成比例）。
**成本**：中高。

## 三、建议的动手顺序（结合当前短板）

```
N1 多城市泛化          ← 先做：消除"只能用西安"的硬伤（面试必问）
N2 地理聚类分天        ← 再做：算法改进 + 实验闭环，成本低、有指标收益
N4 反事实 或 N3 稳健性模拟  ← 选一个做深（推荐 N3，技术深度最高）
N6 主动澄清式抽取      ← 交互设计加分
N5 / N7                ← 按需
N8                     ← 不做
```

**一句话**：你现在的短板不是「功能少」，而是**「只能在一个城市跑」+「所有时间都是确定值」**。
前者是**可用性**（N1 解决），后者是**深度**（N3 解决）。这两个补完，项目从「demo」变成「系统」。
