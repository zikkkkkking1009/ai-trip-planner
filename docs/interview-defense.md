> 背景：中厂 AI 岗面试官第一视角评审指出四颗雷（质量分口径 / 提速倍数 / 并发瓶颈 / 零构建选型）。
> 本文档逐题给出**可查证的答案**，其中规模口径用新增对照实验 `backend/eval_scale.json` 的实测数据。
> 原则：只写可查证事实；简历与自我介绍如引用数字，以本文档口径为准。

## 一、「行程质量分 0.915 是谁定义的？」

**口径**：自定义评分函数，公式 `质量分 = 0.4·通勤得分 + 0.4·无冲突得分 + 0.2·均衡度`（见
`docs/reviews/2026-09-28-zcode-review.md` 与 `eval_gap.py` 的 `_obj`）。

三个诚实声明 + 一个反击点：

1. **权重是自定的**，不是行业标准——如实承认。
2. 但**三方对照里所有方案用同一把尺**（朴素基线 / 本项目求解器 / LLM 直接排期），且
   **硬指标（冲突数、预算违规、未排景点数）不依赖这把尺**：求解器 0 冲突 0 违规是独立校验器
   `constraint_check` 复核的结构性事实，质量分只是附加维度。
3. 权重做过敏感性口径说明：通勤占 0.4 是「旅行体验优先」的定位选择，改权重不改变
   「LLM 直接排期违规 8 次 vs 求解器 0 次」的定性结论。
4. 反击点：面试官问「怎么算的」是好事——50 组场景、固定种子 42、脚本与结果文件全在
   仓库（`eval_results.json` / `eval_gap.json` / `eval_scale.json`），**任何人可复跑**。

## 二、「提速 8 倍，50 个景点还快吗？」

**先纠口径**：「8 倍」不在仓库任何文档与代码里（全仓 grep 可查证）——简历如引用过此数，
应替换为下面的实测口径。

**实测口径**（`tools/eval_scale.py` → `backend/eval_scale.json`，合成坐标=真实西安景点确定性
抖动、通勤为 haversine 直线估算、离线零 API）：

| N 景点 | 启发式(中位) | CP-SAT(time_limit) | CP-SAT 状态 | 质量分对比 |
|-------|------------|--------------------|-------------|-----------|
| 8 | 502ms | **0.13s** | OPTIMAL | 持平（60.9） |
| 14 | 1.2s | 30.1s（撞时限） | FEASIBLE | 持平（94.4） |
| 25 | 1.5s | 60.3s（撞时限） | FEASIBLE | 启发式反高（106.5 vs 105.5） |
| 50 | 1.5s | 120.8s（撞时限） | FEASIBLE | CP-SAT +4%（122.8 vs 117.8） |

**正确结论（比「8 倍」更强）**：

1. **存在工程分界点**：N≤8 时 CP-SAT 又快又准（0.13s 即 OPTIMAL）——小规模该直接用精确求解；
   **N≥14 起 CP-SAT 撞时限只能给 FEASIBLE，启发式 1.5 秒内出解且质量差距 ≤5%**——实时交互场景用启发式是合理选择而非偷懒。
2. 这组数据把「田忌赛马」质询变成「规模-质量-耗时三维权衡」的设计论证；
   且两个求解器**未排景点数完全一致**（约束语义一致性的旁证）。
3. N=25/50 时未排 12/35 属预期：3 天 × 19:00 收班 + 预算 800 本就装不下 50 景，两求解器行为一致。

## 三、「并发 1000 人，哪里先崩？」

按架构自上而下的瓶颈序（无数据库，服务基本无状态）：

1. **最先崩：外部供应商**。每个新计划触发 LLM 抽取（DeepSeek）+ 高德 POI/通勤调用——
   瓶颈是**供应商配额与限频**（高德个人 Key 0.35s 限频是代码里写死的），不是自家 CPU。
   缓解：三级通勤缓存（内存→磁盘→API）已把重复请求挡掉。
2. **其次：限流桶**。`RATE_LIMIT` 按 IP 限频，但花生壳不透传 XFF ⇒ 实为**全场共享一桶**
   （默认 120 req/min，见 docs/deploy-runbook.md）——并发一高先在这里排队/拒绝。
   这是**已知且文档化的**限制，公网部署换隧道即自动生效按 IP。
3. **再次：CP-SAT/求解 CPU**。单次求解 0.5–1.5s（见上表），Python 进程内串行——
   1000 并发会堆 worker；多副本可横向扩（无状态）。
4. **不会崩的**：静态页与 `/demo/*`（零 Key 缓存数据）。
答案要点：先答「外部 API 配额」再答「限流策略」最后才是「计算」，展示的是**系统性排查顺序**而非背数字。

## 四、「为什么前端不用 React/Vue？」

选型主张（不是不会，是**刻意不用**，且有明确代价清单）：

1. **部署约束**：花生壳免费隧道 + 国内弱网访问，单文件零 CDN = 首页只有 2 个请求（HTML + 高德 JS），
   无 node_modules 供应链、无构建产物分发问题——演示场景「打开就有」优先。
2. **可审阅性**：项目是作品集，单文件让审阅者/面试官 clone 即读，无工具链门槛。
3. **代价如实列**：`index.html` 5,077 行，改动的合并冲突面大、无组件隔离、无类型检查——
   这正是 ROADMAP 里 **C1 前端拆分列为 P1** 的原因；触发条件已写明（再加新页面前必须拆）。
4. **边界**：若做多人使用/团队协作形态，会上 Vite + 组件框架并引入状态管理——
   但当前单用户演示形态下，框架只增加复杂度不增加价值。

## 五、其他口径备忘

- 「38 城 375 景」如实回答：**是脚本抓取的高德真实数据，不是技术亮点**——技术亮点在
  泛化机制（城市中心表 + citylimit 抓取 + 参数化测试自动接管 + 人工甄别去商业 POI）。
- 「零用户」：如实承认；演示数据与公网部署是「可用性」证明，不是「被使用」证明。
- LLM 深度：**RAG 模块已落地（R1~R5，2026-10-04）**——BM25+字符 bigram 检索 `GET /ask`
  带引用（R1）→ 引用核查对齐库内实体、景点落真实坐标（R2）→ golden 30 条三臂评测（R3）→
  grounded 生成层 `with_answer=1` 默认关（R4）→ 语料 desc 增强 360 条（R5）。
  评测数据（`backend/eval_rag.json`，增强前 → 增强后）：
  BM25 hit@1 66.7% → **90.0%**、hit@5 70.0% → **100%**、MRR 0.689 → **0.944**；
  向量重排 60.0/70.0/0.647 → 90.0/100/0.950；纯向量 63.3/76.7/0.704 → 86.7/100/0.925。
- 「为什么不上向量？」标准答法（2026-10-05 全量重跑后校准，workbuddy 核查修正）：
  **做了两轮对照实验，结论随数据更新**。R3（语料贫瘠期）：重排三指标全劣化（60.0/0.647 vs 66.7/0.689）；
  R5（desc 增强 360 条后重测）：重排 hit@1 / hit@5 与 BM25 **完全打平**（均 90.0 / 100），MRR 仅微超 **0.006**——
  30 条样本合计 0.2 条的差距，**构不成显著增益**，却要引入 embedding 通道、向量缓存与配额依赖 ⇒ **维持 BM25**。
  ⚠️ **口径要点（背错了会被追问）**：现在**不能说「重排与 BM25 完全同分」**（重排 MRR 0.950 > BM25 0.944），
  也不能说「重排 +0.01」（旧数据残留）——准确表述是「**hit@1/hit@5 打平、MRR +0.006 属噪音**」，
  决策依据是「**增益测不出来**」而非「重排劣化」。
  R3→R5 同时证明了检索的短板**在语料不在算法**：desc 增强把 BM25 hit@1 从 66.7% 拉到 90.0%（hit@5 100%）。
  面试要点：不是「向量不好」，是「数据决定这一步不值得」；旧理由作废就明说——结论跟重测走，
  这正是评测体系的价值：每个采纳/不采纳都有数可依、有前后对照。

- 「客服的『不确定转人工』怎么实现？」（2026-10-07 国内化一期，`backend/support.py`）：
  **转人工不是新闸门，是能力边界的下游动作**——三档决策完全复用 RAG 的 `gap`（unsupported/attr/soft），
  不另造判断（两套口径必然漂移）。差别在**代价**：检索页答错只是少条引用，客服答错误导客户决策，
  所以 unsupported / 空结果在客服侧的动作是**转人工 + 落线索工单**；attr/soft 给部分答案 + ⚠️ 明说缺什么；
  用户发「人工」跳过检索直接落单。评测指标是**转人工正确率**（该转的转了/不该转的没转），
  数据来自会话留痕（每轮记决策档位）。渠道侧（公众号被动回复）**永不烧 LLM**：
  5s 回复时限 × LLM 延迟不可控，两个约束选确定性组句；微信 5s 无回复会重发 ⇒ MsgId 去重。
- 「LLM 成本怎么管？」：三层——**限流**挡滥用（花钱路径全场配额 + 生成独立总闸）、
  **默认关**挡意外（R4 生成层与客服生成层默认 0，显式开才烧）、**台账**回答钱花在哪
  （`llm_ledger.py` 在 5 个运行时 LLM 出口统一打点 purpose/model/tokens/latency，
  `GET /admin/usage` 按用途 × 模型聚合；只记账不改行为，写失败不拖垮业务）。
  面试要点：限流是「防」，台账是「查」，两个都要——只有防没有查，出了成本异常还是不知道谁烧的。
