# 实验报告

本文件记录项目的量化实验：设置、结果、结论、局限。**所有结果均可复现**（固定随机种子 + 脚本提交在仓库）。

复现命令（在 `backend/` 下）：

```bash
python evaluation.py --n 50 --seed 42 --with-llm   # 实验一：排期方案对比
python eval_aligner.py                             # 实验二：实体对齐
python bench_models.py --repeat 5                  # 实验三：模型选型
```

## 实验零｜方法学说明

**为什么要专门说方法学**：本项目的结论都被用于工程决策（选求解器、选模型、路由任务），
如果实验本身不可复现或口径不清，结论就是不可信的。以下三点是硬约束：

1. **随机种子固定**：`evaluation.py` 支持 `--seed`（默认 42）。场景生成随机，同参数下结果可复现。
   *（修正记录：2026-09-18 前未固定种子，历史结果无法复现，已修复。）*
2. **对照方案三者齐备**：朴素装填基线、LLM 直接排期、本项目求解器。缺少任何一个都无法论证"为什么需要算法"。
3. **指标口径写死**：行程质量 `quality = 0.4·(1-通勤占比) + 0.4·(1-冲突率) + 0.2·(1-负载不均衡)`；
   冲突数、预算违规数、通勤占比为硬指标。对齐评测的"判对"定义为归一化后完全相等或互为子串。

**局限（诚实声明）**：场景由程序从 14 个西安景点生成，非真实用户请求；单城市；无用户行为数据；
LLM 基线的方差未做多种子统计（当前为单种子 50 场景）。

## 实验一｜排期方案三方对比

**设置**：50 组程序生成场景，随机种子 42，`--with-llm`（LLM 基线 = 主模型 `deepseek-chat`）。

| 指标 | 朴素装填基线 | **本项目求解器** | LLM 直接排期 |
|------|-------------|----------------|-------------|
| 每计划时间冲突数 | 0.38 | **0** | 0.02 |
| 无冲突率 | 62% | **100%** | 98% |
| 预算违规次数 | 12 | **0** | 8 |
| 通勤时间占比 | 23.5% | **13.1%** | 13.1% |
| 行程质量分 | 0.857 | 0.915 | 0.921 |

**结论**

1. **求解器在硬约束上完胜**：0 冲突、0 预算违规；LLM 直接排期有 8 次预算违规、2% 场景存在时间冲突。
2. **质量分几乎持平**（0.915 vs 0.921）：LLM 在"好看的行程"上并不差，差的是**合规性**。
   这正是"LLM 负责理解、算法负责合规"这一架构决策的实证依据——**不是 LLM 排得不好，而是它不能保证不越界**。
3. **通勤优化有效**：相比朴素基线，通勤占比从 23.5% 降到 13.1%（降 44%）。
4. 求解器结果与换模型前一致（0.915 / 0.131 / 100%），说明**求解器是确定性的，不受 LLM 侧变更影响**——
   这是分层架构的额外收益。

**与历史结果对比**：修正种子前后，求解器指标完全一致；LLM 基线有轻微波动（质量 0.918→0.921，无冲突率 0.96→0.98），
属模型侧方差，不影响结论。

## 实验二｜实体对齐评测

**设置**：20 条人工标注（覆盖西安/北京/成都/杭州，含别名、错别字、非标准简称），判对标准为归一化后相等或互为子串。

| 指标 | 数值 |
|------|------|
| Precision | 90.0% |
| Recall | 90.0% |
| F1 | 90.0% |
| 转人工率（低置信度） | 20.0% |
| POI 检索缓存命中率 | 100%（20/20） |

**失败案例分析**（含金量最高的部分）

| 输入 | 标注期望 | 系统输出（改前） | 失败原因 |
|------|---------|---------|---------|
| 华清池 | 华清宫 | 华清池 | 同义异名：景区更名后高德主名是"华清宫"，而"华清池"作为别名仍能精确命中 POI，打分反而更高。需要引入**名称权威性先验**（主名 > 别名） |
| 紫禁城 | 故宫博物院 | 北京国际雕塑公园-远望紫禁城 | 包含关系误判：几乎不相关的 POI 名称里含"紫禁城"三字，被判为子串匹配。需要**地名前缀长度惩罚 / 行政区一致性校验** |

**转人工设计的价值**：20% 的低置信度样本会走用户点选兜底，这意味着"不确定时不猜"——
在评测口径里它们被计入 miss（Recall 偏低），但在产品上是**可接受的降级**。这是刻意的取舍。

**局限**：20 条样本量偏小，单条样本影响 5 个百分点，统计意义有限（路线图 A3 已列：扩充至 100~200 条）。

### 实验二改进（A7）：结构性规则 + LLM 仲裁，F1 90% → 100%

**方法**（三个机制，全部可独立解释）：

1. **尾部子景点惩罚**：候选名 = 长前缀(≥3字) + 别名在尾部（如「北京国际雕塑公园-远望紫禁城」）时，
   候选的辨识主体是前缀那个 POI，「别名」只是它内部一处观景点的名字——containment 与字符相似度
   都归零。这是结构性规则，不需要词典，先于 LLM 把明显误判挡掉。
2. **主名权威性先验（更名检测）**：搜老名「华清池」时，召回里同时有老名 POI（精确匹配、置信 1.0）
   和多个「华清宫-子点」，且子点**地址引用老名**（「……华清池景区内」）——交叉字段证据证明该景区
   已更名。此时用主名「华清宫」重查一次，采纳主名本体（结果 reason 标记 `renamed_main`）。
3. **LLM 仲裁兜底**：文本打分低于阈值（0.72）时，把已召回候选（名称+类型+地址）交给 LLM 选择，
   硬约束：**答案必须精确等于某个候选名**（防幻觉），LLM 无把握返回空则保持转人工。仲裁结果
   带缓存（`.align_arb_cache.json`，key 含候选集哈希），评测可离线复现。

**改前 / 改后同口径对照**（同 20 条标注、同判定规则，改后首跑含 1 次 amap 主名重查 + 3 次 LLM 仲裁，
复跑全缓存命中）：

| 指标 | 改前 | 改后 |
|------|------|------|
| Precision / Recall / F1 | 90.0% | **100.0%** |
| 判对数 | 18/20 | 20/20 |
| 转人工率 | 20.0% | 15.0% |
| 华清池 | ❌ 华清池 | ✅ 华清宫（主名重查，置信 1.00） |
| 紫禁城 | ❌ 北京国际雕塑公园-远望紫禁城 | ✅ 故宫博物院（LLM 仲裁） |

**未走仲裁的案例说明**：陕历博（clean 候选仅 1 个，仲裁无意义）、回民街与熊猫基地（LLM 无把握
返回空 → 按设计保持转人工，原始预测本身已判对）——「不确定时不猜」的取舍保留。

**行政区一致性校验为什么没做**：尾部惩罚已结构性排除跨区误判（远望紫禁城在石景山，本体在东城），
LLM 仲裁又从语义上兜底；行政区字段（pname/adname）在 v3 接口需要额外请求，边际收益低，不引入。

**局限**：F1 100% 是在 20 条小样本上的结果，不能外推为真实分布准确率；三机制中最强的 LLM 仲裁
依赖外部 API（无 key 环境自动降级为转人工，无硬失败）。A3 扩充标注集后需复测。

## 实验三｜模型选型（主模型 vs 免费模型）

**设置**：三类真实任务，每个模型每任务重复 5 次，取均值与最快值。抽取输入为 101 字的西安三日游攻略。

| 任务 | 主模型 `deepseek-chat` | 免费 `glm-4-flash-250414` | 差距 |
|------|----------------------|--------------------------|------|
| 攻略抽取（长输出，用户等待） | **1.88s**（最快 1.52s） | 12.12s（最快 10.14s） | 慢 6.4 倍 |
| 意图解析（短输出，用户等待） | **0.78s**（最快 0.62s） | 2.56s（最快 0.99s） | 慢 3.3 倍 |
| 评价生成（长输出，后台预取） | **1.98s**（最快 1.58s） | 5.74s（最快 3.96s） | 慢 2.9 倍 |

**免费档候选实测**（同 key 下不同模型 ID，单轮简单请求）：`glm-4-flash-250414` 0.49~0.79s 最快；
`glm-4-flash` 约 1.2s；`glm-4.5-flash` 22s（思考型）；`glm-4.7-flash` 返回 429 过载。

**结论与工程决策（任务路由）**

1. **免费 ≠ 不降速**：在前两类"用户等待"的任务上，免费模型慢 3~6 倍，因此**不替换主模型**。
2. **按任务特性路由，而不是按"轻/重"一刀切**：
   - 攻略抽取 → 主模型（用户等待 + 长输出）
   - 意图解析 → 主模型（用户等待 + 短输出）
   - 评价生成 → **免费模型**（规划完成后后台并发预取，用户点开时已命中缓存，延迟不可感知）
   这样做到了「交互路径不降速 + 生成任务零成本」。
3. **格式遵从性差异**：免费模型会照抄提示词里的模板词（输出"标题: 古城墙"而非"古城墙"），
   已在解析层加正则清洗。**轻量模型必须做输出清洗**，否则功能会"静默降级"。

**一次踩坑记录（方法论价值）**：首版基准脚本只替换了 `editor` 的客户端，而 `extractor` 直接读环境变量，
导致"两个模型跑得一样快"——实际两次都在测主模型。修正后 GLM 抽取从"1.69s"变成"12.12s"。
**教训：基准测试必须验证被测对象真的被替换**（可在结果里加模型名回显）。

## 实验四｜最优解对照（启发式 vs CP-SAT）

**设置**：`solver_cpsat.py` 用 OR-Tools CP-SAT 建同款模型（弧模型 M-TSPTW：时间窗 + 每日时间窗 + 可选住宿锚点往返 + 预算），
50 组场景（同一生成器、seed=42、同一通勤口径），每个实例 CP-SAT 时间上限 8 秒。
目标函数 `obj = 1000·收益 − 通勤分钟数`（收益优先、通勤为次），`gap = (obj_opt − obj_heur)/obj_opt`。

| 指标 | 数值 |
|------|------|
| gap 均值 | **7.57%** |
| gap 中位数 | 5.90% |
| gap 最大 / 最小 | 24.34% / 0.00% |
| gap ≤ 3% 的场景占比 | 46.0% |
| CP-SAT 在 8s 内证明最优的比例 | 52.0% |
| 耗时：启发式 / CP-SAT | **1ms** / 均值 4.18s（最大 8.16s） |
| 平均收益：启发式 → 最优 | 73.5 → **79.4** |
| 平均通勤：启发式 → 最优 | 150.1 → **121.8**（差 23%） |

**结论（与原假设不符，据实记录）**

1. **假设「gap ≤ 3%」不成立**：均值 7.57%，只有 46% 的实例落在 3% 以内。
   *这正是做这个实验的价值——不测就永远以为启发式够好。*
2. **gap 与实例松紧强相关**：
   - 宽松实例（8~10 个景点 / 2~3 天）：gap **0.00%**，启发式与最优完全一致，且只要 **1 毫秒**
   - 紧张实例（12~13 个景点 / 2 天）：gap **21%~24%**——贪心先装满高分景点，
     导致后续高收益组合被时间窗挤掉，2-opt 只在"天内顺序"上局部改进，无法换掉整组选择
3. **瓶颈在"选择"而非"排序"**：通勤差距 23% 说明最优解会为了塞进更多高收益景点而主动绕路，
   启发式的"就近装填"反而是次优结构。
4. **代价对比清楚了**：启发式 1ms / CP-SAT 4.18s（4000 倍）。
   对交互式产品，这个代价不可直接接受，但**完全可以用在离线或"后台优化"路径**。

**由此得到的工程决策**

| 场景 | 选用 | 理由 |
|------|------|------|
| 交互式即时排期（≤14 景点，用户等待） | 启发式 | 1ms；宽松实例已达最优 |
| 紧张实例（景点多、天数少） | 启发式 + CP-SAT 后台改进 | 差距可达 20%+，值得花几秒 |
| 规模再大（>20 景点） | 启发式 + LNS（大邻域搜索） | CP-SAT 在更大规模下求解时间不可控 |

### 改进尝试一：暖启动（hint）— 未观测到收益

把启发式解映射为 CP-SAT 的变量提示（结构与时刻），20 场景对照：

| 指标（20 场景） | 冷启动 | 暖启动 |
|----------------|-------|-------|
| gap 均值（3s 预算） | 8.6% | 8.6% |
| gap 均值（0.5s 预算） | 8.6% | 8.6% |
| CP-SAT 均值耗时 | 1.51s | 1.53s |

**结论：在本项目规模（≤14 景点 / ≤7 天）下，hint 没有带来可测收益** —— CP-SAT 自带搜索启发式
已足够快找到同等质量的解。记录在此，避免后人重复尝试。

> 踩坑：初版实现对所有 `z` 先 hint 0 再 hint 1，**同一变量被 hint 两次**导致模型直接报
> `MODEL_INVALID`（求解结果静默变成 0 收益）。修正方式是先收集 `{变量: 取值}` 再统一应用一次。
> 已加测试 `test_cpsat_warm_start_does_not_break_model` 防回归。

### 改进尝试二：目标下界约束 — 有效的"不差于启发式"硬保证

把启发式的目标值作为约束下界 `obj ≥ obj_heuristic` 加进模型（`target_floor` 参数），
CP-SAT 只能在"不比启发式差"的空间里搜索：

| 实例（13 景点 / 2 天 / 预算 300 / 1 秒预算） | 收益 | 通勤 |
|--------------------------------------------|------|------|
| 启发式 | 59.2 | 181.0 |
| CP-SAT + 下界约束 | **76.5** | **103.0** |

**结论：这是可用的组合策略** —— 启发式 1ms 保证"有解且不差"，若要更优则给精确解 1~3 秒预算，
且下界约束确保不会比启发式更糟（测试 `test_cpsat_not_worse_than_heuristic_with_floor` 守住该性质）。

### 改进尝试三：多起点随机重启（已落地，效果最大）

**动机**：实验四指出瓶颈在"景点选择"（穷举证据：通勤差 23%、收益差 7.4%），而原构造阶段是
**纯分数降序贪心**——确定性顺序一旦选错组合，后续 2-opt/跨日搬运只能在"天内顺序"上局部改进。

**做法**（`solver.py`）：第 0 轮用分数降序（与旧版完全一致，作为保底），随后用**带抖动的顺序**
重跑「贪心构造 + 2-opt + 跨日搬运」，按目标值 `1000·收益 − 通勤` 保留最优的一轮。
固定随机种子保证可复现；时间预算 1.5s 封顶；景点数 < 7 时退化为单次贪心。

**同口径对照（50 场景 / seed=42 / 与同一批 CP-SAT 最优值比较）**

| 指标 | 改造前（纯贪心） | 改造后（多起点） | 变化 |
|------|----------------|----------------|------|
| gap 均值 | 7.53% | **−0.03%** | 归零（负值见下） |
| gap 中位 | 5.89% | **0.00%** | |
| gap 最大 | 24.34% | **0.03%** | |
| gap ≤ 3% 占比 | 46.0% | **100%** | |
| 平均收益 | 73.5 | **79.5**（最优 79.4） | +8.2% |
| 平均通勤 | 150.1 分钟 | **127.7 分钟** | −15% |
| 单次耗时 | ~1 ms | **均值 501 ms / 最大 ~0.9 s** | 仍是交互量级 |

**参数敏感性**（在同一个最差实例上）

| 迭代上限 / 时间预算 | gap | 耗时 |
|-------------------|-----|------|
| 200 / 1.0s | 8.81% | 81 ms |
| 600 / 1.5s | **0.01%** | 248 ms |
| 2000 / 3.0s | −0.00% | 845 ms |

→ 取 **600 / 1.5s**：收益已饱和，耗时仍在交互可接受范围。

**关于负 gap**：gap 定义是与 CP-SAT **在 8 秒内返回的解**相比。部分实例 CP-SAT 只到 FEASIBLE
（未证明最优），而多起点启发式反而找到了更优解 —— 所以出现 −0.08%。这说明两者互补，
也说明"精确解"在有限时间预算下并非永远占优。

**顺带确认**：改造后 2-opt / 跨日搬运的增益空间被多起点吃掉了大部分——瓶颈确实在构造阶段的顺序。

## 实验五｜地理聚类构造（N2）——**负结果**

**动机**：构造阶段按「通勤/分数比」逐个插入，天与天之间没有地理聚类，理论上可能出现
「城东城西各排一半」。猜想：加一轮「按地理位置分组」的构造顺序，让地理相近的景点
连续进入贪心，就能逼出"每天玩一个区域"，把通勤占比压进 10%。

**方法**：`backend/eval_cluster.py` —— 改前/改后**同口径**对照（同一批 50 场景、同种子、
通勤走本地估算以免吃 API 配额）。k-means 用**确定性初始化**（按经度等距取点）以保证可复现；
聚类轮与抖动轮并存，仍然取目标最优。

| 指标 | 关闭聚类 | 开启聚类 | 变化 |
|------|---------|---------|------|
| 通勤占比 | 0.1049 | 0.1049 | **0.0000** |
| 通勤分钟 | 125.2 | 125.2 | 0 |
| 总收益 | 79.46 | 79.46 | 0 |
| 排入景点数 | 10.2 | 10.2 | 0 |
| 耗时 | 469ms | 470ms | +0.8ms |

逐场景：**0 改善 / 0 变差 / 50 持平** —— 逐条核对后确认：聚类轮产出的解**从未被选为最优**。

**归因（含一次真实的实验方法学踩坑）**

1. **首次实验出现了"通勤降了、收益也降"的不可比结果**（20 场景：通勤占比 −0.0007 但收益 −0.23）。
   定位到根因：聚类轮**没有消耗随机数**，导致后续抖动轮的 rng 序列整体错位，
   开启/关闭聚类两条路径探索的根本不是同一批候选 —— 结果不可比，
   而且"取最优 ⇒ 不劣于旧版"的不变量已经被悄悄破坏。
   修复（聚类轮仍消耗一次 rng）后结果变为**完全持平**，说明此前的"改善"是假象。
   → **教训：实验的可比性必须主动验证，不能假设"多跑了一轮所以不会更差"。**
2. 最优化口径是 `1000·收益 − 通勤`，**通勤权重极弱**（1 分钟通勤 ≈ 0.001 分收益）：
   任何"牺牲收益换通勤"的构造成果都会被目标值判为更差，因此聚类轮拿不到"最优"的位置。
3. 600 轮随机抖动 + 2-opt + 跨日搬运已经吃掉了这部分顺序空间
   —— 与实验四的发现一致（多起点也曾把 2-opt/搬运的增益空间吃掉大部分）。

**结论与处置**：`USE_GEO_CLUSTER` **默认关闭**（代码、实验脚本、测试全部保留）。
**复测（2026-09-20，A2 偏好上线后）**：在 `less_walk` 模式下重跑同一脚本
（`eval_cluster.py --pref less_walk --n 50 --seed 42`）——**仍然 0 改善 / 0 变差 / 50 持平**。
所以 N2 不是"条件不对"，而是这条路线本身没有增益：即便通勤权重提到 120，
随机重启 + 2-opt + 跨日搬运 +（A2 新增的）主动放弃景点算子已把顺序空间吃干净了。
原先写的"待 A2 上线后复测"这条**已被实测证伪**，特此更正结论：不建议再在这条路线上投入。

6 个测试守住两条不变量：聚类确定性与正确性、「开启聚类不劣于关闭」。

**局限**：本实验通勤用 haversine 估算，与真实路况下的空间分布可能不同；
换高德真实通勤矩阵后结论需复测（大城市的快速路/单行道会让空间分布更不均匀）。

## 实验六｜A2 偏好权重可调（用户可选"少走路 / 省钱 / 多玩"）

**动机**：用户想要的不是"改某个景点"，而是"这趟更看重什么"。N2 的负结果也指出：
目标函数里通勤权重极弱，导致任何"牺牲收益换通勤"的方案都不会被采纳——所以偏好必须显式化。

**方法**：先**标定**（扫描权重，看指标如何变化），再**对照**（四偏好同批场景）。
脚本 `backend/eval_preference.py`（`--sweep commute|cost` 标定，`--n` 对照）。

### 1) 通勤权重扫描（24 场景，基线 = 现在 balanced 的权重 1.0）

| 通勤权重 | 通勤占比 | 通勤分钟 | 排入景点 | 每少 1 个景点换来 |
|---|---|---|---|---|
| 1（基线） | 0.103 | 122.4 | 10.08 | — |
| 25 / 60 | 0.100 / 0.099 | 117.9 / 117.3 | 10.08 | 景点没少，改善微弱 |
| **120** | **0.088** | **96.5** | 9.88（−0.21） | **7.4 个百分点** ← 性价比拐点 |
| 200 | 0.086 | 93.7 | 9.79 | 6.0 |
| 320 | 0.081 | 84.4 | 9.42 | 3.4 |
| 500 / 800 | 0.068 / 0.007 | 64.8 / 3.8 | 8.29 / 3.29 | 800 已崩（只排 3 个景点） |

门票权重同理标定（放弃一个景点损失 ≈ 1000×9，一张票几十元 → 权重也在百量级）：
权重 120 时门票 282→144 元（省 51%），景点 10.08→8.67；权重 200 时门票降到 22 元但只排 6.29 个。

### 2) 四偏好对照（50 场景，同种子）

| 偏好 | 通勤分钟 | 总门票 | 排入景点 | 总收益 |
|---|---|---|---|---|
| balanced | 125.2 | 285.9 | 10.2 | 79.46 |
| **less_walk** | **100.7**（−24.5） | 265.3 | 10.0（−0.2） | 77.83 |
| **save_money** | 77.5 | **140.9（−51%）** | 8.72（−1.48） | 67.71 |
| **more_spots** | 131.2 | 311.1 | **10.42（+0.22）** | **81.38（+1.9）** |

### 3) 三个关键发现（都是踩过才知道的）

1. **只改目标函数权重，偏好完全没有效果** —— 第一版把 `less_walk` 的通勤权重从 1 调到 40，
   通勤占比**纹丝不动**。根因：构造的插入判据是固定的「通勤/分数」，
   而 2-opt 与跨日搬运**本来就在最小化通勤**；目标函数只在"选哪一"时用，各轮结果又几乎一样。
   → 唯一杠杆是**为省通勤主动放弃远处景点**，因此新增 `_drop_improve` 算子：
   移除某景点若能让目标值提升就移除。balanced 下权重低 → 不会移除（与旧版行为一致，无回归）。
2. **"多玩"调权重同样无效** —— 降低通勤权重后景点数一动不动，因为真正的上限是
   **时间窗**（9:00–18:00 已排满）。→ 改为**放宽时间窗**（每天多玩 1.5 小时），才真的多排了 0.22 个。
3. **实验脚本自己也有坑** —— 第一版扫描只改了 `PREFERENCES` 表、没改 `req.preference`
   （Solver 从请求里读偏好），于是得出"权重完全无效"的**错误结论**，差点把判断搞反。
   修正后曲线才正常。教训：**实验结论异常时，先怀疑实验装置，再怀疑对象。**

### 4) 取值与守卫

- `less_walk.commute = 120`、`save_money.cost = 120`、`more_spots` = 时间窗 +1.5h
- `balanced` 权重保持 `{commute:1, cost:0}`，目标值与旧口径 `1000·收益 − 通勤` **完全一致**
  （有单测守住），因此与 CP-SAT 的 gap 对照不受影响。
- 8 个单测：偏好容错回退、balanced 无回归、三种偏好各自的指标必须真的变化、
  `more_spots` 不得污染调用方传入的 `req`。

**局限**：权重是在西安/程序生成场景上标定的；换到跨度更大的城市（如重庆、山城）
绝对通勤量会变化，但**相对排序**应当稳定——若上线真实通勤矩阵建议复标一次。

## 实验七｜N3 稳健性模拟：**参数敏感性与"建议可不可信"**

**动机**：模拟器输出的"按时概率"依赖噪声参数（停留 0.6~1.6 倍、通勤 σ=0.25）——
这些是**估计值，不是从真实打卡数据标定的**。所以必须回答两个问题：
① 这个百分比能信到什么程度？② "建议去掉某景点"是否稳健？

**方法**：`backend/eval_simulation.py`——同一份紧张行程（西安 2 天 6 景点，时间窗 9:00–15:30）
跑 5 组参数，每组 800 次抽样。

| 参数组 | 按时概率 | Top3 风险点 | 与默认组重合 |
|---|---|---|---|
| 默认(0.6~1.6, σ=0.25) | 21.2% | 西安城墙、回民街、秦始皇兵马俑博物馆 | — |
| 乐观(0.8~1.2, σ=0.15) | 62.4% | 青龙寺、秦始皇兵马俑博物馆、西安城墙 | 2/3 |
| 悲观(0.5~2.0, σ=0.40) | 8.9% | 西安城墙、回民街、秦始皇兵马俑博物馆 | 3/3 |
| 仅停留波动(σ=0) | 12.1% | 回民街、西安城墙、秦始皇兵马俑博物馆 | 3/3 |
| 仅通勤波动(停留=1) | 45.5% | 秦始皇兵马俑博物馆、青龙寺、西安城墙 | 2/3 |

**结论**：
1. **绝对概率不能当精确值**——跨度达 53.5 个百分点（8.9% ~ 62.4%）。
   → 界面文案因此写成"稳健性估计 + 波动假设说明"，而不是给一个孤零零的百分比。
2. **风险点排序是稳健的**——"西安城墙"在**全部 5 组参数**下都进 Top3，
   各组 Top3 与默认组重合 2~3/3。→ 产品里"**建议去掉谁**"是可信的，这比"概率多少"更有用。

**顺带暴露的产品问题（记为待办 N3b）**：短时间窗下求解器"纸面可行"地排了 6~7 个景点，
模拟却显示按时概率只有 3%~16% —— **纸面可行 ≠ 现实可行**。
现在的做法是"事后告知 + 给建议"，更彻底的做法是把稳健性做成**排程约束**（预留缓冲，
例如要求 P80 按时）。这是下一步，不在本实验范围。

**局限（诚实记录）**：参数未用真实数据校准；`respect_open_hour=True` 只建模了"早到等开门"，
没有建模"景点提前关门""排队"等。若要上线，可取少量真实打卡数据反推 σ。

## 结论汇总（工程动作清单）

| 实验结论 | 落到代码/配置的动作 |
|---------|-------------------|
| 求解器保证 100% 合规，LLM 直排会违规 | 确立"LLM 理解 + 求解器合规"分层架构；求解器为硬约束唯一出口 |
| 对齐 F1 90%，两类失败模式明确 | A7 已落地：尾部子景点惩罚 + 主名权威性先验（更名重查）+ LLM 仲裁兜底，F1 100%（见实验二改进节） |
| 地理聚类构造**无增量收益**（balanced 与 less_walk 两种偏好下复测均为 0 改善 / 0 变差） | N2：`USE_GEO_CLUSTER` 默认关闭，代码/脚本/测试保留；原写「待 A2 上线复测」**已被实测证伪**，不建议再投入。**顺带修掉一个真问题：聚类轮漏消耗 rng 会让"不劣于旧版"的不变量失效** |
| 免费模型在交互任务上慢 3~6 倍 | 意图解析改回主模型；免费模型仅用于后台评价生成 |
| 轻量模型会照抄模板词 | 解析层加输出清洗 |
| 种子未固定导致历史结果不可复现 | `evaluation.py` 加 `--seed`（默认 42） |
